# Configuration guide

Configure every value in the target tenant. The distributed solution and
example settings intentionally contain no credentials, tenant IDs, environment
URLs, user data, or live connection IDs.

## Environment variables

| Schema name | Import label | Required value | Example |
|---|---|---|---|
| `ft_EnvURL` | Env URL | Absolute HTTPS URL of the target Dataverse environment, without a trailing slash | `https://<environment-name>.crm.dynamics.com` |
| `ft_LicensingClientId` | Licensing Connector Client ID | Application (client) ID of the customer-owned Entra app registration | `<application-client-id>` |

Don't use a tenant ID for `ft_LicensingClientId`.

## Microsoft Entra app registration

Create a customer-owned, single-tenant app registration for the included
**Get Licensing Info** connector.

Configure these delegated Microsoft Graph permissions:

| Permission | Type | Purpose |
|---|---|---|
| `User.Read` | Delegated | Read the signed-in user's basic profile |
| `LicenseAssignment.Read.All` | Delegated | Read user license assignments |
| `offline_access` | Delegated | Maintain the delegated connection |

No Microsoft Graph write permission is required or expected. Apply
administrator consent according to your tenant policy.

After solution import:

1. Open the custom connector in the target environment.
2. Copy its generated redirect URI.
3. Add that exact value as a **Web** redirect URI on the app registration.
   Preserve existing redirect URIs used by other environments.
4. Create a client secret according to organizational policy.
5. Copy the secret **Value**, not its secret ID, from the same app registration
   whose application ID is configured for the connector. Enter it only into the
   target connector's **Security** configuration.
6. Select **Update connector** and wait for the update to succeed. Entering a
   value without saving the connector does not update its OAuth configuration.
7. Create or reconnect a connection and complete delegated sign-in and consent.

Store and rotate the secret through your approved secret-management process.
The secret isn't part of the solution and must never be committed.

### Licensing authentication troubleshooting

| Symptom | Corrective action |
|---|---|
| `AADSTS50011` redirect URI mismatch | Register the exact Web redirect URI generated by the connector in the target environment; don't copy a different environment's URI |
| `AADSTS7000215` or `invalid_client` | Verify that the connector uses a valid secret **Value** for the configured app, save with **Update connector**, and reconnect; don't use the secret ID or paste the secret into chat |
| **Create** or **Reconnect** appears unresponsive | Check for an OAuth window or blocked-popup indicator and any error in the connection dialog; a fresh attempt can expose an OAuth error that the connection list doesn't show |
| The agent shows **Connection Required** | Use **Set up connection** to establish the signed-in operator's delegated connection, then select **Retry** or start a fresh conversation |

Confirm the target environment before changing connector security. After
repair, verify the connection is **Connected**, bind both licensing connection
references to the working connection, and run a real agent licensing lookup.
A connected status alone does not establish that the agent's tool can execute.

## Connections and connection references

The solution uses:

- Microsoft Dataverse connections for read tools and the five controlled-write
  flows;
- the included custom connector for read-only Microsoft Graph licensing
  queries.

`config/deployment-settings.example.json` lists four connection references
because both the Copilot agent and cloud flows reference the connectors.
Populate every `ConnectionId` in a private deployment copy. A connection ID is
environment-specific even though it isn't a credential.

All Dataverse reads and writes must run in the signed-in user's own Dataverse
security context. Don't substitute a broadly privileged shared service
connection. Microsoft Entra ID sign-in is required in every channel.

Verify **Run as the signed-in user** on the Microsoft Dataverse connection in
each of the five agent flows: **Preview Role Assignment**, **Execute Role
Assignment**, **Preview Team Membership**, **Execute Team Membership**, and
**Cancel Confirmation**. An active flow or a connected connection reference
alone does not verify this setting. In exported flow JSON, the Dataverse
connection reference must contain `"impersonation": {"source": "invoker"}`.
All five cloud flows must retain this invoker-identity setting.

If this setting is missing in a managed deployment, correct it in the unmanaged
source and promote a new package. For an unmanaged development installation,
repair the affected flows, verify they remain active, and export the corrected
solution. Independently test allowed and denied behavior with appropriate
operators before production use.

In the managed package, the agent's instructions, skills and tools, and the
cloud flows, are locked. Customers who need a different model or other changes
should import the unmanaged package into a development environment and manage
it through their own ALM. Any change to the model, instructions, tools, flows, channels, or
connections is the customer's responsibility and is outside the configuration
Microsoft reviewed. See the [Transparency Note](./transparency-note.md).

## Dataverse security

All five cloud flows (**Preview Role Assignment**, **Execute Role Assignment**,
**Preview Team Membership**, **Execute Team Membership**, and
**Cancel Confirmation**) run with the invoking administrator's identity
("Use invoker's connection"). Dataverse applies that administrator's
privileges to every read and write; an administrator cannot assign a role
containing privileges they do not hold.

Operators need Create, Read and Write privileges on the **Admin Agent Write
Log** table (`ft_adminagentwritelog`).

The agent doesn't elevate permissions. Operators need only the privileges
required for the data and actions they are authorized to use. At minimum,
review access to:

- system users, business units, security roles, teams, and memberships;
- field security profiles when that scenario is enabled;
- Dataverse audit data for audit-history scenarios;
- association privileges needed to assign an existing role or add an existing
  team member;
- Create, Read and Write privileges on the **Admin Agent Write Log** table
  (`ft_adminagentwritelog`).

Use separate test operators to confirm both allowed and denied behavior.
Results can differ between operators because Dataverse applies each caller's
permissions.

## Auditing and retention

Enable Dataverse auditing and choose a retention period that meets your
organization's requirements before enabling audit-dependent scenarios. An
absent access record is reported as Unknown, not proof of inactivity.

The solution can process identity, security-configuration, audit, licensing,
conversation, and change-control data. Review:

- Dataverse audit retention;
- Copilot Studio and channel transcript retention;
- Power Automate run-history retention;
- access to the write-log table;
- any Application Insights or tenant analytics configuration.

## Data policy

Confirm that the applicable Power Platform data policy permits the Dataverse
connector and the custom Microsoft Graph connector in the same business data
group and blocks unapproved connector combinations. See
[Data policies in Power Platform](https://learn.microsoft.com/power-platform/admin/wp-data-loss-prevention).

## Post-configuration checklist

- [ ] Environment URL points to the intended target.
- [ ] Client ID belongs to the intended customer tenant.
- [ ] Redirect URI exactly matches the connector-generated value.
- [ ] Only delegated read permissions are granted to Microsoft Graph.
- [ ] Connector secret is stored only in the target environment.
- [ ] All connection references resolve successfully.
- [ ] Dataverse connections use the intended user context.
- [ ] All five agent flows have **Run as the signed-in user** enabled.
- [ ] Flows are enabled and tested.
- [ ] Auditing and retention are configured.
- [ ] Data policy allows only approved connector combinations.
- [ ] Agent audience is limited to an administrator security group or channel.
- [ ] Microsoft Entra ID sign-in is required in every channel.
- [ ] Every enabled channel has been validated separately.
